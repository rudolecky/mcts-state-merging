# Classical MCTS Merging on Connect Four (No LLM)

## Question

Every prior H3 result in this project entangled two things: does merging help search, and
does the *learned* merge criterion work. This isolates the first question in its purest form:
plain UCB1 MCTS, random rollouts, exact-board-state transposition merging (no LLM, no learned
metric, no neural net). Domain: Connect Four, reusing `connect_four_engine.py` unchanged.

## Setup

- `src/mcts_phase0/classical_mcts.py`: standard single-simulation-per-iteration MCTS. Baseline
  keys nodes by move-path-from-root (plain tree, structurally can't collide). Treatment keys
  nodes by `canonical_state(board, to_move)` (real transposition table). One shared
  implementation, one key function swapped — same `merge_enabled` philosophy as `search.py`.
- Selection: classical UCB1 (`Q + c*sqrt(ln(N_parent)/n_edge)`, `c=1.4`), not PUCT — no policy
  network exists here to supply a prior.
- Metric: per-puzzle solve rate over 50 independent repeats per condition per budget (vs. one
  binary outcome per puzzle in every LLM experiment — affordable here since pure-Python MCTS
  is orders of magnitude cheaper than LLM sampling).
- Forced-win puzzles generated by `connect_four.generate_puzzles` — exact difficulty by
  construction (`k_plies`), no calibration pass needed.
- Verified: `pytest tests/test_classical_mcts.py` (9 tests) + full suite (155 passed) green.

**Verdict: zero solve-rate benefit from merging, at every budget and depth tested.** The one

deep-floor budgets (10) through deep-ceiling budgets (400), and across a 3x range of puzzle
depth (k_plies 3→5) — not a ceiling-effect artifact, checked directly.

Merging is real and substantial: up to **23% fewer unique nodes** at k=5/budget=400 (351.9→270.9).
Transpositions genuinely occur and genuinely get deduplicated. They just don't move solve rate.

## Mechanism

This sharply contrasts the LLM-based H3 result on the identical Connect Four domain (large,
robust, significant merging benefit). The reason: **UCB1's own selection policy already
prevents the failure mode merging was fixing in the LLM setting.**

In the LLM harness, each of K independently-sampled candidates at an expansion got its own
isolated value estimate; near-duplicate candidates (transpositions) were common and each
consumed a full LLM call while contributing almost nothing beyond what its twin already
contributed — budget spent on redundant branches was, in an important sense, wasted, and merging
recovered that waste by pooling statistics across the duplicates.

Classical MCTS's `untried_moves` bookkeeping + UCB1 structurally can't waste budget this way:
every node tries each of its own legal moves exactly once before ever repeating one, and revisits
are driven by UCB1's own exploitation/exploration balance, not blind resampling. A baseline
tree's duplicate branches (reached via different move orders) each get their own independent,
UCB1-directed exploration — a promising duplicate still gets adequately explored on its own
merits, with no need to borrow statistics from its twin. There's no analog of the LLM setting's
"most of K samples land on the same node and get thrown away" pathology for merging to fix.

This reframes the project's core H3 finding precisely: **merging's accuracy benefit was a fix
for LLM independent-sampling's specific redundancy problem, not a universal graph-search-beats-
tree-search property.** Where the underlying search algorithm already has a built-in
anti-redundancy mechanism (UCB1's untried-move tracking), transposition merging still happens
and still saves memory/node count, but buys no accuracy at matched budget. This is consistent
with real MCTS game engines' actual practice: transposition tables there are valued for
compute/wall-clock savings (skip re-simulating a known position) or memory, not for improving
search quality at a fixed simulation count — a distinction this project's LLM-centric framing
never had reason to draw until now.

One implementation note worth flagging: this harness always runs a fresh rollout on every
expansion, merge-hit or not (i.e. a transposition doesn't skip the simulation, only the fresh
`MCTSNode` allocation) — so the observed null isn't an artifact of merging silently saving
rollout compute and creating an unfair budget mismatch; both conditions do the same amount of
rollout work per expansion, one-for-one.

## Status

Closed. Clean, well-powered (50 repeats × up to 30 puzzles × 8 budget points across 2 depths),
decisive null with a mechanistically grounded explanation. No further parameter sweeps
(larger `c`, different puzzle distributions) planned — the result is consistent across the full
range already tried and the mechanism story doesn't predict a different outcome from tuning `c`
or distribution shape.
