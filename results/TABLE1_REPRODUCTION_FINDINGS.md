# Reproducing a Slice of Table 1: GBFS vs. GUCT vs. GUCT-Uniform on Real IPC Instances

## Question

The user asked to reproduce arXiv:2405.18248's Table 1. Scoped to a minimal slice (see the plan
file): our three already-in-hand algorithms -- GBFS, plain GUCT, and GUCT-Uniform -- on `h^FF`
only, no PO/DE, against a handful of *real* IPC benchmark instances (not our own generated
puzzles), to check whether the paper's own reported ranking (GUCT-Uniform > GBFS > plain GUCT)
shows up directionally. It does not show up the way expected -- and the reason why turned out to
be the single most direct, decisive confirmation of this entire project's thesis found anywhere,
surfacing unprompted while trying to reproduce someone else's result on their own kind of data.

## Setup

- **Real instances**, vendored from `github.com/aibasel/downward-benchmarks` (commit
  `e21d49c2cb61d147a46c5966f2581bf6fd422b9f`, the standard PDDL benchmark repository the planning
  community uses) -- not generated by this project. 5 Blocksworld instances
  (`probBLOCKS-{4..8}-0`) and 7 Gripper instances (`prob{01,02,03,04,06,08,10}`). Provenance and
  exact files recorded in `data/pddl_benchmarks/README.md`.
- **Parsed and grounded through pyperplan's own PDDL pipeline** (`Parser` -> `grounding.ground`),
  confirmed directly from `pyperplan/planner.py`'s own CLI glue code -- not our hand-built
  Blocksworld engine. This project's existing generic engine wrappers and every function in
  `guct_uniform_blocksworld.py` needed zero changes to run on these: none of that code is
  Blocksworld-specific internally.
- **Protocol matches the paper's own where it's the thing being reproduced**: 10,000
  node-evaluation cap, 5 seeds per randomized algorithm, `h^FF` (pyperplan's own `hFFHeuristic`,
  the exact class the paper uses).
- New: `paper_repro/pddl_loader.py` (PDDL -> `Task`), `paper_repro/capped_gbfs.py` (a small
  heapq-based greedy best-first search with an exact node-evaluation cap -- pyperplan's own GBFS
  has no such cap and could run unboundedly long on a real instance), `paper_repro/guct.py` (plain
  GUCT: leaf-count NEC, Monte Carlo/average backup, `c=1.4` as a documented default absent the
  paper's own tuned value -- a genuinely different algorithm from both `classical_mcts_blocksworld.py`
  and `guct_uniform_blocksworld.py`). GUCT-Uniform itself is reused unchanged from
  `guct_uniform_blocksworld.py`.
- Verified: `tests/test_table1_repro.py` (7 new tests: PDDL loader against real vendored fixtures,
  `capped_gbfs` solving a real instance, plain GUCT's NEC formula against hand-computed values,
  Monte Carlo backup pooling by **average** -- a third distinct backup rule now tested explicitly,
  alongside `classical_mcts_blocksworld.py`'s sum/count and `guct_uniform_blocksworld.py`'s min --
  and a cycle-avoidance check on a real reversible instance) + full suite (283 passed) green.

## The ranking does not match the paper -- and diverges in opposite directions per domain

On **Blocksworld**, GUCT-Uniform-in-tree-mode (exactly the paper's own algorithm, no merging --
confirmed the paper never runs one) is by a wide margin the **worst** algorithm tested: it solves
almost nothing (1/25 seed-runs), while GBFS (5/5) and even plain GUCT (15/25) both clearly beat
it. This is the *opposite* ranking from the paper's own Table 1, which reports GUCT-Uniform
beating GBFS by a wide margin overall (606.4 vs. 538/539 instances solved, out of 539, under
`h^FF`).

On **Gripper**, the paper's own claimed advantage shows up cleanly: GUCT-Uniform-in-tree-mode
solves every single instance (35/35), including two (`prob08`, `prob10`) where plain GUCT fails
completely (0/5 each) -- exactly the kind of result the paper's Table 1 reports.

**Same algorithm, same implementation, same protocol -- opposite outcome depending on domain.**
That divergence is itself the finding worth explaining, not a contradiction to paper over.

## Mechanism: why Blocksworld breaks tree-mode GUCT-Uniform specifically

`capped_gbfs.py` deduplicates visited states as a matter of textbook definition (`if succ_state in
visited: continue` -- ordinary GBFS bookkeeping, not an enhancement). Tree-mode GUCT-Uniform has no
such thing: confirmed from the paper's own text, it's a plain tree-based open list, so every path
that reaches an already-seen state creates a brand-new, unrelated node for it. Combined with
`LCB1-Uniform`'s own confirmed lack of a self-limiting exploration term (established earlier this
session -- its score can keep looking more attractive the more an edge gets pulled, rather than
converging, the paper's own "escape the plateau quickly" design choice), the search can commit hard
to one narrow branch and keep re-deriving the same small cluster of already-visited states as
"new" tree nodes, over and over, without ever being forced back to try root's other options --
confirmed directly: on `probBLOCKS-4-0`, tree-mode GUCT-Uniform still hadn't solved it after
50,000 evaluations (5x the paper's own cap), while GBFS solves the identical instance in 24.
Enabling merging alone -- no other change -- fixes this instantly: 100% solved at every budget
tested, down to a cap as low as 100 evaluations. Blocksworld's own reversible, densely-transposing
structure (the exact property `BLOCKSWORLD_FINDINGS.md` and `BLOCKSWORLD_GUCT_UNIFORM_FINDINGS.md`
already identified) is precisely what makes this failure mode so severe here and not on Gripper,
whose branching apparently doesn't trap the search in a small revisited cluster the same way at
these instance sizes.

This is the sharpest version of this project's whole thesis found anywhere: not "merging makes an
already-working search a bit more efficient," but **merging is the difference between an algorithm
that essentially never solves a real, easy benchmark instance and one that solves it every time**
-- on data this project didn't generate, using an algorithm faithfully reimplemented from someone
else's paper, under that paper's own stated protocol.

## Scope and limitations (same honesty bar as the prior findings doc)

- **N is tiny relative to the paper's own** (12 instances here vs. 539 `h^FF`-compatible instances
  across 24 domains there). This is a directional check, not a numerically comparable
  reproduction, and was scoped that way deliberately (see the plan file).
- **Not the same instances as the paper** -- these are real IPC files, but the paper's own 24-domain
  selection and exact instance list were never sourced; ours is an independently chosen subset of
  two domains.
- **GBFS's 100% here is a ceiling effect of small instance sizes**, not evidence GBFS is superior
  in general -- the paper's own Table 1 shows GUCT-Uniform beating GBFS in aggregate across many
  domains, and `probBLOCKS-8-0` already needed 698 evaluations for GBFS (climbing fast); larger
  real instances would likely eventually defeat plain GBFS too.
- **Plain GUCT's `c=1.4`** is this project's own reasonable default, not the paper's own tuned
  value (never stated in the visible text) -- a different `c` could shift plain GUCT's specific
  numbers, though is unlikely to change the qualitative Blocksworld-vs-Gripper divergence, since
  that divergence traces to the backup rule and dedup, not the exploration constant.
- **Formula fidelity, not validated absolute performance** -- same caveat as
  `BLOCKSWORLD_GUCT_UNIFORM_FINDINGS.md`: the algorithm is built faithfully from the paper's own
  stated formulas and unit-tested against hand-computed values, but was never cross-validated
  against the paper's own reported numbers on a shared instance set.

## Status

Closed. This is not the ranking-confirmation the "reproduce Table 1" request set out to find --
it's something more useful: a real, externally-sourced instance on which the paper's own proposed
algorithm, run exactly as the paper itself always runs it, essentially fails outright, and where
this project's own manipulation (merging) is precisely what fixes it. No further follow-up is
queued by default.
