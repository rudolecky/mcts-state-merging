# A True Self-Play AlphaZero Clone on Connect Four: Does Merging Still Help?

## Question

Every merge-vs-tree comparison in this project used one of two search algorithms: classical
UCB1-MCTS (random rollout, no learning -- the 4-domain classical arc) or PUCT with a *degenerate*
uniform-1/K prior standing in for a real policy network (the LLM H3 arc). Neither is what
AlphaZero actually does: real PUCT uses a trained network's genuine, non-uniform policy as the
prior, and evaluates leaves with the network's value head directly, no rollout. This builds that
-- a true self-play AlphaZero clone on Connect Four -- and asks whether merging still helps once
the prior is real, not a stand-in for one.

## What was built

`src/mcts_phase0/alphazero/`, entirely new, zero existing files touched:

- `network.py` -- a small CNN (2 input planes, AlphaZero's own current-player-relative
  canonicalization; 3 conv blocks, 48 channels; policy head over 5 columns, value head in [0,1]
  matching this project's fixed-perspective convention elsewhere, but note: PUCT's own value is
  *not* fixed-perspective, see below).
- `puct.py` -- real PUCT (`Q + c_puct * P(s,a) * sqrt(N(s)) / (1+N(s,a))`), leaf evaluation via
  one network forward pass, no rollout at all. Deliberately different value convention from every
  other module here: AlphaZero's value is *current-player-relative*, flipping sign (by complement,
  since this project uses [0,1] not AlphaZero's original [-1,+1]) at every ply during backup -- a
  well-known AlphaZero-clone bug class if gotten wrong, so it got a dedicated hand-computed unit
  test before anything else touched it. Every legal move gets exactly one edge per node, created
  eagerly the first time that node is visited (one network call gives the policy for all of them
  at once) -- structurally the same "each move tried at most once per node" guarantee classical
  UCB1-MCTS has, just for a different reason (PUCT's prior already tells selection which untried
  moves are worth trying, so there's no need to force trying each one before repeating).
- `selfplay.py`, `train.py`, `run_selfplay_train.py` -- self-play game generation (full games from
  the empty board, Dirichlet root noise, temperature-then-greedy move selection), replay buffer +
  training step (masked cross-entropy + value MSE), and the driving CLI with checkpoint/resume.
- `run_merge_experiment.py` -- the actual payoff comparison, on the same k_plies-controlled
  puzzle set (`connect_four.generate_puzzles`) used throughout this project.

**One real training bug found and fixed before any real run**: masking illegal-move logits with
literal `-inf` before the cross-entropy sum produces `0 * (-inf) = NaN` under IEEE float
semantics for every illegal column (whose target is legitimately 0) -- guaranteed to NaN out on
any batch containing a non-empty board, i.e. almost every real batch. Fixed by masking with a
large finite negative instead (the same fix used everywhere for attention masking). Caught via a
direct debug trace before trusting any training run, not discovered downstream in a loss curve.

**One infrastructure bug found on first resume attempt**: PyTorch 2.6 changed `torch.load`'s
default to `weights_only=True`, which refuses to unpickle the checkpoint's custom
`SelfPlayExample` objects. Fixed with an explicit `weights_only=False` (safe here -- the
checkpoint is self-generated by this same script, never loaded from an untrusted source).

## Training: converged cleanly

120 iterations, 3,000 self-play games total, ~40 minutes combined wall-clock on CPU (no GPU
needed at this network/board size). Training loss fell smoothly and monotonically from 1.36 to a
stable plateau around 0.90-0.92 over the last ~25 iterations, with no instability, divergence, or
NaN at any point across the entire run -- genuinely good for a from-scratch self-play RL run, a
class of training famously prone to silent failure. Win rate vs. a uniformly-random opponent rose
from 0.725 to a stable 0.85-0.975 range; puzzle-solving at a deliberately tight fixed budget
(k_plies=3 forced wins, only 8 PUCT simulations per move -- tight enough that a better prior
actually has to matter) rose from 0.60 to a stable 0.85-1.00 range. Both metrics plateaued
alongside the loss, the expected signature of genuine convergence for this network/board size,
not a run cut off mid-improvement.

## Results: merging still doesn't help, and it's the predicted outcome, not a surprise

Same 40-puzzle set (k_plies=3, `connect_four.generate_puzzles`, seed 0), budgets swept from deep
floor to deep ceiling:

| budget | baseline | treatment | nodes base&rarr;treat |
|---|---|---|---|
| 2 | 0/40 | 0/40 | 10.3&rarr;10.3 |
| 3 | 24/40 | 24/40 | 14.6&rarr;14.6 |
| 5 | 32/40 | 32/40 | 22.1&rarr;22.1 |
| 10 | 35/40 | 35/40 | 35.9&rarr;35.7 |
| 25 | 40/40 | 40/40 | 70.3&rarr;68.3 |
| 50 | 40/40 | 40/40 | 112.7&rarr;106.3 |
| 100 | 40/40 | 40/40 | 178.8&rarr;164.1 |

**Every single budget is an exact tie**, across a genuine floor-to-ceiling range (0/40 at budget
2 through 40/40 by budget 25) -- not a ceiling artifact. Real merging occurs and grows with
budget (up to 8% fewer unique nodes at budget=100), the same "dedup happens, doesn't help"
pattern seen throughout the classical UCB1 arc, not a sign the mechanism is inert.

This is the outcome the project's own mechanism theory predicted going in, not a fresh discovery:
`puct.py`'s eager-child-creation design gives every legal move exactly one edge per node,
structurally the same "tried at most once" guarantee classical UCB1-MCTS has -- just enforced for
a different reason (PUCT's own prior already ranks untried moves, so nothing needs forcing). The
K-sampling ablations (`CONNECT_FOUR_KSAMPLE_FINDINGS.md`, `MORRIS_KSAMPLE_FINDINGS.md`) already
established that guidance quality only creates a redundancy-driven merge opportunity when the
expansion mechanism itself lacks that structural guarantee -- true of the LLM harness's batched
K-independent-candidate sampling, false of every classical-shaped expansion in this project. Real
AlphaZero-style PUCT, even with a genuinely trained, non-uniform, non-degenerate policy from 3,000
self-play games, is built the classical-shaped way on this dimension: it never draws the same
move twice at one node, so there's nothing latent for a better or worse prior to unlock.

## What this settles

The open question from the original scoping conversation -- "does merging help once the prior is
real, not a stand-in for one" -- is answered directly: no, not on Connect Four, and the reason
generalizes cleanly from everything already established. The prior's *source* (uniform, frozen
LLM projection, or genuinely trained self-play network) was never the load-bearing variable in
this project's whole investigation. The expansion mechanism's structural relationship to
redundant exploration is -- and real AlphaZero-style PUCT shares Connect Four's classical UCB1
structure on exactly that dimension, so it inherits the same null.

## Status

Closed. A full self-play-to-convergence AlphaZero clone was built and trained specifically to
test this, not assumed from the K-sampling ablations' logic alone -- the actual experiment
confirms what that reasoning predicted, across a properly swept floor-to-ceiling budget range,
with real (if unhelpful) merging activity visible in the node counts throughout.
